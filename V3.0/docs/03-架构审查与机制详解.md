## 1. 总体架构

(图 1:`figures/fig1_system_arch.pdf`)

```
用户层    手机QQ主号(浔的昳 2690468347) + 手机QQ清浔号(手动回复)
            │ 私聊消息 / message_sent(自身消息上报)
协议层    NapCat napcat-v4(Docker, OneBot v11 协议端, 登录接管号 1145077465)
            │ 反向 WebSocket ws://127.0.0.1:8091/ws?access_token=...
服务层    mychat-server-v3(8091, FastAPI 单端口)
            ├─ onebot/ws_client   入站事件(鉴权 fail-closed/self_id 过滤/防抖/代答拦截/手动回复)
            ├─ pipeline           九阶段管线(人设/记忆/心情/LLM/评分/落库)
            ├─ adapter/onebot     出站(array 格式防 CQ 注入 + reply_guard 守卫)
            ├─ takeover           代答 pending 队列 + 手动回复记录
            └─ REST API + 面板    PC(七页) + 移动端 /m(七页)
支撑层    mychat-redis-v3(独立数据, 与 V2.0 完全隔离)
          LLM Providers(GLM/DeepSeek/硅基流动, 按任务路由)
          GPT-SoVITS TTS(frp 隧道 → 用户本地 4060 机器)
```

核心设计原则:

- **平台无关内核**:pipeline/记忆/评分/人设/心情/插件零 import 平台代码,OneBot 适配只发生在 `onebot/ws_client.py`(入站)与 `adapter/onebot.py`(出站)两个边界。
- **数据隔离**:V3.0 独立 redis(`chatbot_v3_net` 网络 + `redis-data-v3` 卷),与 V2.0(8000, 官方机器人)并存互不影响。
- **软失败哲学**:除"落库"是硬契约外,评分/记忆/心情/TTS/插件全部 try 吞异常降级,主回复链路永不因附属系统挂掉而中断。

## 2. 消息处理管线

(图 2:`figures/fig2_pipeline.pdf`)

### 2.1 入站分流(ws_client.py)

```
NapCat 反向WS帧
→ _dispatch_response(:85)      Action 响应(echo tag 匹配 future;send 响应同步登记 message_id)
→ _handle_event(:250)
    ├─ self_id != 接管号        忽略(双号场景)
    ├─ message_sent(私聊)      → _handle_manual_sent(:308) 手动回复(异步分发)
    │    ① _confirm_own_send    自发去重(命中 _sent_msg_ids 忽略;在途竞态等待)
    │    ② 接收方 = target_id(NapCat 坑:user_id=senderUin=自己)
    │    ③ 陌生人门控(无会话/代答/待答 → 不记录)
    │    ④ takeover.record_manual_reply(详见 §6.4)
    ├─ message(私聊)
    │    ├─ 代答模式开启        → pending 队列(纯媒体占位 [图片]/[语音] 入队)
    │    └─ 否则                → _schedule_debounce(:423) 连发防抖(默认 2s 窗口合并)
    └─ 其余(meta/群聊)         忽略
```

### 2.2 管线九阶段(pipeline/runner.py:34-88)

```
钩子 ON_MESSAGE_IN(可 STOP 丢消息)
① load_history      最近 20 条对话(Working 层)
② persona_inject    人设卡 → system_prompt + provider/model 绑定
②.5 memory_retrieve 四级记忆召回 → memory_block(见 §5.3)
②.6 mood_inject     心情档位 hint 追加 system_prompt
钩子 ON_BEFORE_LLM  (continuous_send 思考延迟 3-5s / time_aware 时间标签 / reply_enhance 攒话)
③ tool_loop | llm_stream   有工具走 function-calling 循环(≤5 轮),否则流式生成
钩子 ON_AFTER_LLM
②.6' mood_update    回复关键词 → mood 值
钩子 ON_MESSAGE_OUT  (tts_reply 发语音 priority=300 / continuous_send 分段 priority=400)
④ run_post_reply_chain = stage_save → stage_score → stage_memory_write
   (统一副作用链, pipeline 与 takeover 共用, 架构收口 #1)
```

关键不变量:score 依赖 save 写入的 `reply_mid`;memory 依赖 `reply_text`;save 硬失败(落库是回合契约),score/memory 软失败。mood_update 不在链内(pipeline 在 save 前、takeover 在 memory 后,时序语义不同)。

### 2.3 出站(adapter/onebot.py + reply_guard.py)

```
send_text(oid, content, human_authored)
→ human_authored=False ? sanitize_reply(content) : 原文      # admin 代答/手动文本跳守卫
→ sanitize_reply = 错误签名兜底(8 条正则, 命中→"（刚刚走神啦，能再说一次吗～）")
                  + strip_trailing_period(句号铁律: 剥句末。/. 小数保护 3.5 不动)
→ call_action("send_private_msg", message=[{"type":"text","data":{"text":...}}])
   # array 格式: 回复文本中的 [CQ:...] 字面量不会被 NapCat 解析成媒体/At(防注入)
```

## 3. 人格系统

### 3.1 PersonaCard(persona/models.py:94-154)

顶层字段:`name/description/user_description/user_alias/personality/scenario/creator_notes` + 嵌套 `profile`(age/gender/occupation/appearance/race/speech_style/catchphrase)、`preferences`(likes/dislikes)、`relationship`(relation/greeting)、`example_dialogue`(few-shot)、`dynamic_state`(mood/status/energy)、`model`(provider/model 绑定)、`history`(反推快照链, max 20)、`version`(乐观锁)。

### 3.2 system_prompt 组装(persona/renderer.py:98-140)

固定段顺序,非空才输出,段间空行:

```
【核心人设指令】{creator_notes}
【背景设定】{description}
【人物画像】年龄:X、性别:X、职业/身份:X、种族:X、外貌:X、说话风格:X、口头禅:X
【性格】{personality}
【喜好与厌恶】喜欢:a、b / 厌恶:c、d
【关于{user_label}】{user_description}          ← user_label = user_alias(如"煜君"), 无则"用户"
【与{user_label}的关系】{relationship.relation}
【开场白】{relationship.greeting}
【场景示例】{scenario}
【示例对话】{user_label}:{...} / 角色:{...}     ← 最多 5 条, 单行截断 200 字
【当前状态】心情:{dynamic_state.mood} 状态:{...} 精力:{...}
```

最终 LLM 收到的 system 消息(阶段拼装,stages.py:109-124):

```
render_system_prompt 输出(末尾第一次 OUTPUT_CONTRACT)
+ "\n\n" + memory_block(记忆召回, §5.3)
+ mood hint(如 "\n[当前心情:平静 ◌,语气平稳自然,不特别起伏]")
+ time_aware 时间标签(如 "\n[当前时间:夏季·深夜]")
+ OUTPUT_CONTRACT(第二次, 置最末权重最高)
然后 + history(20 条) + [user: 本次消息]
```

### 3.3 OUTPUT_CONTRACT 全文(renderer.py:32-42)

```
【输出契约】
你在用手机和对方发消息聊天。只输出你要发给对方的那句话本身,像微信打字一样自然。
禁止用括号(全角（）或半角())、方括号、星号包裹动作、神态、心理或语气说明(不要出现如（轻声笑了）（微笑）（摸头）*叹气*这类描写)。
不要旁白,不要解释自己正用什么语气说话,不要分点、列清单或加标题。
标点铁律:整条回复绝不用句号(。和.)结尾——语气靠换行和『~』『呀』『嗯』等语气词表达;问号、感叹号、省略号可以用。
诚实优先:基于已知事实和记忆回答,不确定或不知道的直接说"哎？""不知道",不要编造细节、不要凭空捏造事实或承诺。
```

(2026-07-06 引入根治舞台指示;2026-08-17 V3.0 增标点铁律,出口层 reply_guard 另有确定性 strip 双保险。)

### 3.4 人设反推的写入口

反推只可写 14 个白名单字段(reverse_infer.py:51-70),核心身份(name/id/avatar/model/plugins)**永不被反推改写**;`personality/scenario/description` 挂顶层,其余嵌套进 profile/preferences/relationship;每字段有长度上限(catchphrase 30/personality 300/description 400…)。

## 4. 心情系统

(mood/service.py)5 档默认(happy/pleased/calm/down/sad, 区间左闭右开无缝覆盖 [0,1]),每档:`score_bias`(happy+6 ~ sad-6) + `bias_noise=3`(评分补偿噪声) + `prompt_hint`(注入语气) + kaomoji。

闭环:`inject_hint`(每轮注入) → `apply_emotion`(回复关键词 ±mood_step=0.1, 正词表如 开心/喜欢/想你, 负词表如 难过/好烦) → `bias_for`(评分补偿 = score_bias + uniform(-3,3)) → `decay_loop`(每 60s 向 0.5 回归 0.05)。

## 5. 记忆层实现详解

(图 3:`figures/fig3_memory.pdf`)

### 5.1 四级结构与 Redis 键(memory/store.py:31-37)

| 层 | 键模板 | 类型 | 语义 | TTL |
|---|---|---|---|---|
| Core 核心记忆 | `mychat:mem:{oid}:core` | String(JSON 数组) | 高重要度/关系事实,**常驻注入不参与检索打分** | 无 |
| Working 工作记忆 | (委托 chat_store) | block 三层 | 最近对话原文滑窗(20 条, get_history 直读) | — |
| Episodic 情景记忆 | `mychat:mem:{oid}:episodic` | ZSet(score=created_ts) | 每 12 轮 LLM 摘要, 检索取最近 3 条;keep 20 条 | 无 |
| Reflect 反思 | `mychat:mem:{oid}:reflect` | List | 每 5 次摘要触发一次高层规律提炼 | 无 |
| Long-term 长期记忆 | `mychat:mem:{oid}:long` | Hash(field=mid) | 抽取/巩固的事实, 检索召回主战场 | 无 |
| 记忆向量 | `mychat:mem:{oid}:vec:{mid}` | String(list[float]) | GLM embedding-3(2048 维), 检索/去重用 | 无 |

全部记忆键**不设 TTL**——生命周期完全由"软遗忘标记 + forget_tick 物理清理"管理(用进废退)。

### 5.2 MemoryItem 全字段(memory/models.py:39-99)

```
id           mem_{uuid12}
content      记忆文本(论断, 角色第一人称口吻)
category     fact | preference | relationship | event | personality(默认 fact)
importance   0~1(LLM 写入时评定; 默认 0.5)
emotion      0~1 情感强度(影响衰减第 4 项)
created_ts / last_access_ts / access_count     (召回即 touch: 重置衰减+计数, 间隔重复效应)
forgotten    软遗忘标记(可恢复)
source       dialog | roleplay | manual | import | proxy | extract
locked       锁定防遗忘(手动)
—— 三要素(2026-08-13 借鉴 angel_memory)——
reason       为什么值得记(含金量)
tags         自由标签(上限 5, 检索入口)
useful_score 用进废退评分 0~1(RL 增减, 默认=importance)
tier         -1 自动(由 useful_score 推档) / 0/1/2 手动档
```

### 5.3 检索逻辑(coordinator.retrieve → retriever)

```
stage_memory_retrieve(user_text)
→ store.get_core(oid)              Core 全量(常驻)
→ store.get_episodic(oid, 3)       最近 3 条情景摘要
→ store.get_all_long_term(oid)     未遗忘全量(候选池)
→ BM25Retriever.rank               第一路: 词法
     分词: 正则 [一-龥]|[a-zA-Z0-9]+ (中文单字+英文词, lower)
     score = Σ IDF(q)·TF(q,d)·(k1+1) / (TF(q,d)+k1·(1-b+b·|d|/avgdl)),  k1=1.5 b=0.75
     IDF = log((n-df+0.5)/(df+0.5)+1), 语料=本轮候选自身
→ coordinator._embedding_rerank    第二路: 向量
     query embed(GLM embedding-3) → get_vecs_bulk 批量取已有向量
     → 懒 embed: 无向量候选现场补(首次检索自动覆盖全库)
     → cosine_similarity(query, v)
→ rrf_fuse(ranked_bm25, ranked_emb)   RRF 融合: score = 1/(60+rank_a) + 1/(60+rank_b)
     (单路命中也保留; k=60)
→ sample_weighted                  softmax 加权随机采样 top-5(temperature=1, 防确定性僵化;
     memory_weighted_sample=False 时确定性 top-K)
→ store.touch_long_term(hit_mids)  召回即访问(衰减重置)
→ render → memory_block:
     【核心记忆】- ...\n【相关长期记忆】- ...\n【近期对话摘要】- ...
→ ctx.memory_meta = {"hit_mids": [...]}    ← 供 RL credit assignment(§6.5)
```

### 5.4 写入链(on_turn_complete, 回合后异步)

```
每轮:  _learn_user_alias(最近 6 条扫自报称呼正则 → persona.user_alias 最新覆盖)
每 12 轮: episodic 摘要(summarize, 取最近 6 条) → append_episodic
          每 5 次摘要再触发 reflect(高层规律提炼)
每 6 轮:  extract_facts_batch 事实抽取(取最近 12 条) → _parse_facts 契约解析
          → 评分联动: 本轮分 ≥85 每条 fact importance+0.1 / <60 -0.1
          → 持 per-oid 锁逐条 _upsert_fact_dedup:
              cosine ≥ 0.85(无向量降级 Jaccard ≥ 0.3)命中 → 合并:
                  access_count+1; importance/emotion 取 max;
                  reason 取首个非空; tags 并集(≤5); useful_score 取 max(巩固不重置)
              未命中 → 新建 MemoryItem(useful_score 初始=importance)
          → core 升级: importance ≥ 0.8 或 category=relationship
          → sign≠0 时 _apply_score_to_recalled(RL, §6.5)
```

### 5.5 记忆压缩提示词(encoder.py, 逐字)

**summarize(情景摘要, 每 12 轮)** — `{label}` = user_alias(如"煜君"), 未配置为"用户":

```
请用一两句中文概括以下对话的关键信息(事实/偏好/事件),只输出概括,不要寒暄。
注意:只概括 {label}(user 一方)明确陈述的事实;角色(我)一方的承诺/虚构/假设若 {label} 未确认,不要当成事实写进概括(防幻觉固化进情景记忆):
{dialog}
```

**extract_facts_batch(长期事实抽取, 每 6 轮)**:

```
你在为【角色本人】整理长期记忆。以下是角色与{label}最近的若干轮对话。请以角色第一人称('我'指角色自己)视角,从中抽取角色值得长期记住的认知——关于{label}的特点/偏好/事件、角色与{label}的关系、角色自身的事。
【防幻觉铁律——必须遵守】
1. 只把'{label}说的话'(user 那行)当作事实来源。角色(我)的回复里提到的事——尤其承诺、计划、假设、虚构(例如角色说'下周带你去吃椰子鸡'但{label}从没提过)——若{label}没有明确确认,绝对不要抽成记忆。
2. {label}亲口陈述的偏好/事件才记;角色回复里的话只在{label}本轮或之前确认过时才记。
3. 严格区分'我'(角色)与'{label}'(对方),切勿把角色名字/特征记成{label}的。
content 必须像角色本人回忆心上人那样自然记下——绝不用'用户'这种疏离称呼,用你对TA的称呼;多记带'我'的关系视角(如'{label}喜欢我''我和{label}是恋人'),客观事实也用角色口吻(如'我叫清浔')。

{dialog}

每条记忆还需给出:reason(为什么这条值得长期记,含金量,没有则空串)、tags(1-3 个简短分类标签,如['喜好','日常'])。
严格只输出一个 JSON 数组,每个元素形如 {"content": str, "importance": 0-1, "emotion": 0-1, "category": "fact|preference|relationship|event|personality", "reason": str, "tags": [str]},没有则返回 []。
```

(第 6 行"content 必须像角色本人回忆心上人那样…"是 V3.0 记忆人称拟人化改句,提交 9551fc3;防幻觉铁律是 2026-07-06 B-3,根治"椰子鸡幻觉自我固化"。)

**consolidate_facts(睡眠巩固, forget_tick 每 6h 末尾)**:与 batch 版同构,输入改最近 20 条情景摘要。(已知接线瑕疵:consolidation.py:41 调用未传 user_alias,label 恒为"用户"。)

**reflect(反思)**:

```
请根据以下近期对话摘要,提炼一两句关于用户的高层规律/偏好/关系结论:
{joined}
```

### 5.6 衰减闭环(用进废退, forgetting.py + forget_tick)

```
retain_score = 0.4·importance + 0.3·recency_decay + 0.15·log1p(access_count) + 0.15·emotion
recency_decay = exp(-0.693 · 距上次访问小时数 / 72h)     ← 召回 touch 即重置(间隔重复)
三档 should_forget:
  tier≥0 手动档优先; tier=-1 自动: useful_score≥0.7→T2 永不 / ≥0.3→T1 评分驱动 / 否则 T0
  T0 自然衰减: retain_score < 0.3 → 忘
  T1 评分驱动: useful_score < 0.3 → 忘
  T2 / locked: 永不
forget_tick(每 6h, background_maintenance):
  ① 软遗忘(should_forget 命中 → forgotten=True 可恢复)
  ② 上限淘汰(>200 条按 retain_score 升序, locked 豁免)
  ③ 物理清理(被软遗忘且创建超 30 天 → HDEL + DEL 向量)
  ④ 睡眠巩固(episodic 摘要 → 巩固 fact 重要性≥0.6 入 long-term → episodic 裁到 20 条)
```

## 6. 评分机制与 RL 闭环

(图 4:`figures/fig4_rl_loop.pdf`)

### 6.1 评审提示词与四元组

**_llm_score(score/service.py:91-98, 逐字)**:

```
你是人设契合度评审。请严格对照下方【角色人设】,评估这条【角色回复】在语气、性格、说话风格、人设一致性上的契合度,打 0-100 的基础分(越高越符合人设,与心情无关),并给出简短理由(一句话,指出契合或偏离之处)。
严格只输出一个 JSON 对象:{"score": <0-100 整数>, "reason": <一句话理由>}。

【角色人设】
{persona_brief}          ← 直接复用 render_system_prompt 输出作评审基准

【角色回复(待评)】
{reply_text}
```

四元组(公式唯一来源 quad.py:14-20):

```
score_base    LLM 基础分(人设契合度, 与心情无关)
mood_at_score 评分时刻 mood 值
mood_bias     档位 score_bias + uniform(-3, 3)   (happy+6 ~ sad-6 ± 噪声)
score         = clamp(round(score_base + mood_bias), 0, 100)
classify:     score ≥ 85 → positive / < 60 → negative / 其余 neutral(不采样)
```

| source | 反推标注 | 权威 | 写入入口 |
|---|---|---|---|
| correction | [管理员纠正] | 黄金标准 | 面板改分填纠正回复(原内容不动) |

### 6.3 反推(reverse_infer,策略更新器)

**_llm_extract 提炼提示词(逐字, reverse_infer.py:188-209)**:

```
你是人设分析师。以下是某角色在与用户对话中获得高分的优秀回复(正样本,契合人设应保持的风格),以及获得低分的偏离回复(负样本,应避免的风格)。请据此提炼该角色的人设字段。
只输出一个 JSON 对象,键为人设字段名,值为提炼结果。
可选字段:personality, speech_style, catchphrase, age, gender, occupation, appearance, race, likes(字符串数组), dislikes(字符串数组), relationship, greeting, scenario, description。
只输出有把握的字段,没有依据就不要输出该字段。严格只输出 JSON,不要解释。
【风格提炼约束——必须遵守】
speech_style / personality 只描述说话的语气、用词习惯、口头禅(如'说话简短直接''爱用语气词''偶尔俏皮'),目标是像真人微信聊天一样自然。
绝对不要总结成'使用括号动作描写''加舞台指示/旁白''用（轻声笑了）这类格式'——任何鼓励括号动作/旁白/颜文字堆砌的描述都禁止输出。

【样本来源说明——重要】
每条样本前标注了来源,权威度从高到低:[管理员纠正]=管理员对不当回复的亲自改写(黄金标准,最优先采信);[管理员亲手回复]=管理员直接以角色身份发出的真实回复(同为黄金标准,最优先采信);[真实对话]=与真用户的实际对话(权威依据);[训练剧本]=人工录入的训练样本(参考补充,可能含设定性/非自然对话内容)。
提炼人设风格时优先依据 [管理员纠正] 和 [管理员亲手回复] 和 [真实对话] 样本,[训练剧本] 仅作补充参考,勿被其设定性措辞带偏。

【高分优秀回复(正样本,应贴合的风格)】
{pos 前 20 条}

【低分偏离回复(负样本,应避免的风格)】
{neg 前 10 条}
```

两步契约:`dry_run`(样本→提炼→diff→token 暂存 Redis 600s)→ 人工确认 `apply`(凭 token 取 diff → snapshot 快照入 history 链 → 写字段 → 一次性删 token 防重放)。diff 保护:字段白名单 14 个 / drift>60% 跳过 / ≤6 字段 / mode=fill_empty 已有值不覆盖 / 快照可 rollback。触发点:面板按钮 + LLM 工具(仅 dry_run)——**全部人工/半自动,无定时自动触发**。

### 6.4 手动干预三入口(奖励信号的人工增强)

1. **手动改分** manual_set_score:覆盖 score_base(保留历史心情),样本清旧按新分重收;可附纠正回复(corrected,恒正样本 source=correction,原内容不动)。
2. **删除联动**:删 ai/proxy 有分消息 → 先清 pos/neg 同 mid 旧样本 → 写 neg(训练价值保留)。
3. **手动回复**(2026-09-07):管理员用清浔 QQ 亲手回 → drain 待答队列 + 配对落库 + 样本恒正 source=manual score=100(占位 [语音] 等不入样本);三级降级(链失败→归档→回灌队列)。

### 6.5 RL 闭环判定:策略 → 行动 → 奖励 → 更新

**结论:存在完整闭环,形态是 bandit 式离线策略优化(人在环),而非在线梯度学习。**

| RL 要素 | 系统对应 | 代码证据 |
|---|---|---|
| **策略 π**(决定"清浔怎么说话") | ① PersonaCard 字段(personality/speech_style/catchphrase…) ② 记忆内容(召回注入 memory_block,影响回复) ③ 心情 prompt_hint ④ OUTPUT_CONTRACT | stages.py:58-106 |
| **行动 a** | LLM 回复生成与表达(tool_loop/llm_stream + 分段多气泡 + 思考延迟 + TTS);人工行动(代答/手动回复=示范数据) | runner.py:63-71, plugins |
| **奖励 r** | ① LLM-as-judge 对照人设打分(+mood_bias) ② 人工改分 ③ 纠正回复(金 100) ④ 手动回复(恒正 100) ⑤ 删除=负信号 | score/service.py:82-170 |
| **更新 θ**(奖励改写策略参数) | **θ₁ 人设反推**:pos/neg 样本 → LLM 提炼 → 人工确认 → 改 14 白名单字段(快照可回滚) **θ₂ 记忆强化**:本轮被召回记忆(hit_mids)useful_score 集体 ±0.1 → 三档衰减(用进废退) **θ₃ 心情**:apply_emotion 关键词迁移 mood(影响下一轮 bias 与 hint) | reverse_infer.py / coordinator.py:206-225 / mood/service.py:163 |

**人格优化 × 记忆系统是否打通?——打通,且有三条链路:**

1. **评分→记忆→人格(θ₂→θ₁ 串联)**:同一评分信号先做记忆 credit assignment(useful_score 决定哪些记忆存活并持续注入 prompt),再经样本队列驱动反推改人设字段——记忆是"策略参数"的一部分,被奖励塑形。
2. **记忆内容直供反推语料**:正负样本本身是回复文本,而回复由"人设+记忆上下文"共同生成——反推间接学到了"哪些记忆引导出了好回复"。
3. **共用奖励源与作者身份**:手动回复(manual)同时是记忆编码输入(配对落库+on_turn_complete)与反推黄金样本([管理员亲手回复] 最高权威);纠正回复(correction)同理——人工示范一次,两个系统同时更新。

**闭环的 8 个缺口(诚实清单,均有 file:line 证据):**

1. neutral 不采样(60-84 无梯度,边界样本信息丢弃)
2. 反推须人工 apply 且无自动触发(更新频率=管理员手点,非在线学习)
3. 奖励是 LLM-as-judge 非真实环境反馈——**用户真实不满只经 apply_emotion 关键词进 mood,不回流 score/样本**,"用户不满但评审给高分"存在盲区(部分被人工三入口补)
4. mood_bias 噪声(±3 随机)使 85/60 阈值边界归类不可复现(设计意图拟人)
5. credit assignment 粗粒度:召回记忆集体 ±δ 不区分单条贡献;且只在每 6 轮的抽取轮结算
6. 评分对象只有 ai/proxy 回复;主动发送/无待答手动插话不评分
7. roleplay 样本 score 无心情项,与 live 两种口径共用阈值
8. useful_score 达 T2 升 core 仅存在于注释,未实现(coordinator.py:300-303)
