## 1. 引言

定义云端 Redis 与客户端本地 SQLite/文件的存储结构、Key 规范、数据生命周期与同步策略。记忆系统的语义分层见 `06-记忆系统设计`，本文聚焦**物理存储**。

## 2. 存储总览

| 存储 | 位置 | 职责 |
|---|---|---|
| Redis | 云端（Docker） | 聊天记录、人设、记忆、动态状态、离线消息、配额计数（权威源） |
| SQLite | 客户端本地 | 聊天记录缓存、会话配置（离线可读） |
| 文件系统 | 云端 + 本地 | 人设图片、头像、表情包、聊天背景等静态资源 |

**权威源原则**：Redis 为准，客户端本地为缓存副本；冲突以 Redis 为准，重连增量同步。

## 3. Redis 数据结构

> Key 前缀规范：`mychat:<域>:<id>[:<子>]`。所有时间戳为 Unix 毫秒。

### 3.1 聊天记录（F-C-04）

| Key | 类型 | 说明 |
|---|---|---|
| `mychat:chat:{object_id}:timeline` | **Sorted Set** | score=`ts`，member=`msg_id`；按时间序索引消息 |
| `mychat:msg:{msg_id}` | **Hash** | 消息详情：`object_id, role(user/ai/proxy), text, attachments(JSON), ts, mood, status, deleted` |

- 删除消息（F-C-10）：置 `deleted=1` + 记 `delete_reason`（`out_of_character` 等），保留以供人格负反馈，而非物理删。
- 撤回（F-C-10）：仅限 `role=user`，置 `recalled=1`。
- 保存上限（F-C-04）：配置 `max_messages` / `max_days`，超额从 timeline 尾部淘汰并归档/删除对应 msg Hash。

> M2 实现阶段简化为 `mychat:chat:{object_id}` List（每元素 `{role, content, ts, msg_type, mid}`），上述 timeline + msg Hash 精细结构为后续增强；工作记忆（见 §3.3）直接复用此 List。

### 3.2 人设（F-S-02）

| Key | 类型 | 说明 |
|---|---|---|
| `mychat:persona:{id}` | **String(JSON)** | 人设完整 JSON（schema 见 `03-接口` §5） |
| `mychat:persona:index` | **Set** | 所有人设 id |

人设文件同时落盘 `server/data/persona/{id}.json`（F-S-02「本地 JSON 持久化」），Redis 与文件双写，启动时从文件重建索引。

### 3.3 记忆系统（存储层，语义见 06；M3 升级为四级）

| Key | 类型 | 说明 |
|---|---|---|
| `mychat:mem:{object_id}:core` | **String(JSON)** | 核心记忆：人设静态指令 + 用户核心画像（姓名/关键关系/绝对偏好），常驻全量注入，不参与召回裁剪 |
| `mychat:chat:{object_id}` | **List** | 工作记忆：最近 N 轮原文，**复用 §3.1 chat_store**，滑动窗口 |
| `mychat:mem:{object_id}:episodic` | **Sorted Set** score=`ts` | 情景记忆：对话摘要条目（member=JSON `{summary, span}`）；设 TTL + 活跃度衰减 |
| `mychat:mem:{object_id}:reflect` | **List** | 反思条目：跨对话高层归纳 `{reflection, ts, span}` |
| `mychat:mem:{object_id}:long` | **Hash** field=mid | 长期记忆：每条 `{id, content, category, importance, emotion, created_ts, last_access_ts, access_count, forgotten, source}` |

- 四级层级（Core / Working / Episodic / Long-term）的语义、编码/检索/遗忘算法见 06；M3 完整规格见 `09-M3实现规格`。
- `category`：fact / preference / relationship / event / personality；`emotion`：0~1 情感强度，影响衰减；`source`：dialog / import / proxy / extract（记忆来源）。
- 遗忘：依据 `importance × recency_decay × access_count × emotion` 计算保留分（retain）；`forgotten=1` 为软遗忘标记（可恢复）；用户手动遗忘直接置 `forgotten=1`，定期物理清理。

### 3.4 动态状态（F-C-05 / F-S-04）

| Key | 类型 | 说明 |
|---|---|---|
| `mychat:state:{object_id}` | **Hash** | `mood, status, energy, updated_ts` |

### 3.5 离线消息与同步

| Key | 类型 | 说明 |
|---|---|---|
| `mychat:outbox:{client_id}` | **List** | 客户端离线期间的待推消息（上线后 `sync_req` 拉取） |

### 3.6 配额计数（F-P-02 图像生成日上限等）

| Key | 类型 | 说明 |
|---|---|---|
| `mychat:quota:{object_id}:img:{yyyymmdd}` | **String(int)** | `INCR` 自增；`EXPIRE` 到当日 24:00；超阈值则聊天对象自主拒绝 |

## 4. 客户端 SQLite 本地模型

### 4.1 messages（缓存）

```sql
CREATE TABLE messages (
  msg_id      TEXT PRIMARY KEY,
  object_id   TEXT NOT NULL,
  role        TEXT NOT NULL,           -- user / ai / proxy
  text        TEXT,
  attachments TEXT,                     -- JSON
  ts          INTEGER NOT NULL,
  mood        TEXT,
  status      TEXT,
  deleted     INTEGER DEFAULT 0,
  recalled    INTEGER DEFAULT 0,
  synced      INTEGER DEFAULT 0         -- 是否已与云端确认
);
CREATE INDEX idx_msg_obj_ts ON messages(object_id, ts);
```

### 4.2 config（本地配置）

```sql
CREATE TABLE config (key TEXT PRIMARY KEY, value TEXT);
```

## 6. 数据同步策略

- **在线**：客户端发消息 → 本地 SQLite 落库（`synced=0`）→ WS 发服务端 → 服务端写 Redis → 回 `ai_done` 时一并确认 → 客户端置 `synced=1`。
- **离线**：本地继续落库（`synced=0`），重连后 `sync_req(since_ts=最后同步ts)` → 服务端 `sync_resp` 返回增量 → 客户端合并、对齐 `synced`。
- **冲突**：以 Redis 为准；本地未同步的发送在重连后补发并按服务端时间戳重排。

## 7. 数据生命周期

| 场景 | 策略 |
|---|---|
| 保存上限 | 到达 `max_messages` 或 `max_days` 时，按 `ts` 升序淘汰最旧消息（timeline + msg Hash） |
| 情景记忆 | 摘要 TTL 自动过期 + 活跃度衰减 |
| 长期记忆 | 遗忘评分机制（见 06），`forgotten` 标记后可定期物理清理 |
| Redis 持久化 | 开启 AOF/RDB，防容器重启丢数据 |
| 备份 | `scripts/backup` 定时 dump（RDB）+ persona 文件 |
