## 1. 引言

### 1.1 编写目的

本文档对「MyChat 智能陪伴聊天机器人」项目（PyCharm 模块名 `Mychat`）进行工程化的需求规格描述，作为后续技术架构设计、接口设计、数据模型设计、开发计划与最终验收的基准。原始需求来源于 `Ref/Reference` 文件，本文档对其进行结构化、编号化、去歧义化整理。

### 1.2 项目背景

本项目旨在实现一款**带有人格与记忆系统的多模态 AI 陪伴聊天软件**，采用**服务端 + 客户端双端架构**：

- **服务端**：部署在云服务器，7×24 小时在线，承载大模型对接、人格/记忆/插件核心逻辑、Web 管理面板。
- **客户端**：部署在 Windows 11 的桌面软件，负责多模态交互展示与桌宠形态。

参考实现：AstrBot（架构/插件系统）、爱语 APP（UI/交互参考）、19 个 AstrBot 社区插件（功能借鉴）。

### 1.3 术语与缩略语

| 术语 | 含义 |
|---|---|
| 聊天对象 / ChatObject | 用户可创建的多个 AI 角色，每个有独立人设、模型配置、记忆、状态 |
| 人设 / Persona | 定义聊天对象的性格、语言风格、外貌、场景等的长文本配置（JSON） |
| 人性化信息 | 心情、风格、当前状态、特殊回复等随时间/对话动态变化的属性 |
| 记忆系统 | 长短期记忆分层存储 + 遗忘机制 |
| 桌宠 | 客户端最小化后呈现的桌面悬浮交互形态 |
| 代人聊天 | 用户手动扮演聊天对象回复，系统记录并用于反推/优化人设 |
| LLM Provider | 大模型服务源（GLM / DeepSeek / 硅基流动 等） |
| 钩子 / Hook | 在消息处理流水线特定节点插入自定义逻辑的扩展点 |
| MCP | Model Context Protocol，模型上下文协议，用于工具/资源扩展 |

## 2. 总体描述

### 2.1 产品定位

一款**单人专属、强人格、强记忆**的多模态 AI 陪伴聊天桌面软件。区别于通用 AI 助手，本产品强调：拟人化人格、长期记忆与情感连续性、多模态表达（文字/语音/图像/表情包）、可扩展插件生态。

### 2.2 用户与角色

| 角色 | 说明 |
|---|---|
| 主用户（User） | 唯一的人类使用者，1 对 1 场景，创建并管理多个聊天对象 |
| 聊天对象（ChatObject） | AI 角色，由人设驱动，被动响应 + 自主发消息 |
| 管理员 | 通过 Web 面板配置人设、模型、插件（单人项目下即主用户本人） |

> 约束：**仅 1 对 1 场景，不做高并发多客户端设计**。

### 2.3 运行环境

| 端 | 环境 |
|---|---|
| 服务端 | 云服务器，IPv4 `43.140.219.99`，OS：CentOS 7，root 权限，7×24 在线；已安装 Docker（用于 Redis 等服务） |
| 客户端 | Windows 11 桌面操作系统 |
| 数据库 | Redis（云端，via Docker）+ 客户端本地持久化 |
| 网络 | 客户端 ↔ 服务端实时通信（需保持实时响应） |

### 2.4 设计约束

- C-01：服务端部署于指定 CentOS 7 云服务器，须 root 部署。
- C-02：仅 1 对 1，不支持多用户并发。
- C-03：服务端须 7×24 在线，随时响应客户端。
- C-04：须提供可视化 Web 面板（提供 URL 即可访问）。
- C-05：客户端为 Win11 原生桌面软件，非 Web 页面。
- C-06：参考 AstrBot 插件系统设计插件机制。
- C-07：所有敏感凭据（服务器口令、API Key、数据库密码）不得硬编码或纳入版本管理，统一放 `.env`。
- C-08：项目类型，代码头部注释遵循「功能说明 + 作者李文煜 + 日期 + 变更日志」风格；文档/注释统一中文。

### 2.5 假设与依赖

- 假设服务端可稳定访问公网，客户端可稳定连接服务端。
- 依赖外部 LLM API（GLM / DeepSeek / 硅基流动）的可用性与配额。
- 依赖 Docker 环境（服务端）。

## 3. 功能需求

> 优先级：P0=必须、P1=重要、P2=可后续迭代。

### 3.1 客户端功能需求

| 编号 | 名称 | 描述 | 优先级 |
|---|---|---|---|
| F-C-01 | 多模态消息收发 | 用户可发送/接收 文字、图像、语音、表情包；界面简洁，参考微信单人聊天 | P0 |
| F-C-02 | 多聊天对象管理 | 可创建多个聊天对象，每个独立配置人设 + 大模型 API；**配置部分在服务端**完成 | P0 |
| F-C-03 | LLM 聊天 | 基于大模型实现聊天；须支持接入 **GLM、DeepSeek、硅基流动** 三类 API | P0 |
| F-C-04 | 聊天记录持久化 | 本地持久化保存聊天记录，可设保存上限；每条记录须附带**时间、心情、状态**等信息；本地保存后**还需上传云端 Redis** | P0 |
| F-C-05 | 人性化信息设定 | 设计聊天对象的**心情、风格、当前状态**等动态属性与**特殊回复**；支持**导入部分聊天记录→学习总结→反向自设定人设** | P1 |
| F-C-06 | 多级记忆系统 | 设计长/短期记忆存储；**参考人类记忆机制实现遗忘**（自主遗忘 + 手动遗忘各一部分） | P0 |
| F-C-07 | 多模态理解与工具 | 聊天对象能识别用户发送的**图像、语音**；可调用**钩子或 MCP**理解内容；支持**联网搜索** | P1 |
| F-C-08 | 表情包管理 | 支持导入表情包（JPG 格式，参考微信导入方案）；聊天对象能**自主查找/选用表情包** | P1 |
| F-C-09 | 7×24 在线 | 聊天对象启动后 7×24 在线；后端逻辑在云服务器，前端仅做展示 | P0 |
| F-C-10 | 消息删除与撤回 | **删除**：用户/聊天对象删除某条消息，视为「该回复不符合人格」，用于反向自设定人格；**撤回**：用户撤回自己已发送消息，用于修改发送错误 | P0 |
| F-C-11 | 桌宠形态 | 界面简洁，不全屏，类似微信单人聊天；可设**聊天背景图片**；**最小化后变为桌宠**（带动态效果的白色浮动圆圈外观）；点击桌宠打开聊天界面，点开最小化又变回桌宠；**桌宠态收到消息时上下抖动** | P1 |

### 3.2 服务端功能需求

| 编号 | 名称 | 描述 | 优先级 |
|---|---|---|---|
| F-S-01 | Web 管理面板 | 提供 URL 即可访问的可视化面板，实现配置功能；**参考 AstrBot 实现插件功能**，支持插件配置 | P0 |
| F-S-02 | 人设创建与持久化 | 面板内创建/设定人设；支持**人设 JSON 导入**与**本地 JSON 持久化保存**；人设结构参考 `persona_*.json`，且应包含**人设语言与图片**；用户可**上传人设图片** | P0 |
| F-S-03 | 代人聊天 | 一键开关大模型；开启后**由用户代人聊天对象回答用户**；该对话同样被记录，用于人格信息较少时**反向优化人格文件** | P0 |
| F-S-04 | 插件工程化 | 插件须**工程化、模版化**；**多插件同时接入不冲突**；**一键开关插件**；可**为不同聊天对象配置不同插件**；须含**动态心情、时间观念、自主发消息**等功能型插件 | P1 |

### 3.3 插件功能需求

| 编号 | 名称 | 描述 | 优先级 |
|---|---|---|---|
| F-P-01 | 语音合成插件 | 合成并发送聊天对象的语音（TTS） | P1 |
| F-P-02 | 图像合成插件 | 基于人设文件中上传的图片，调用智能体/MCP/网页提示词生成相关图片；**须有限制**：当日合成次数达上限后，聊天对象**自主拒绝** | P1 |
| F-P-03 | 表情包生成器插件 | 生成表情包 | P2 |
| ~~F-P-04~~ | ~~lmarena 对接插件~~（已移除） | 2026-06-19 用户决定不做 lmarena，本需求取消 | - |
| F-P-05 | 回复增强插件 | 支持将多条回复合并展示；支持接收**多条用户输入后再回复**，并能**自主判断接受多少输入** | P2 |

## 4. 非功能需求

### 4.1 性能（NFR-P）
- NFR-P-01：单用户场景，消息端到端响应延迟以满足「实时响应」体感为目标（具体阈值在架构设计阶段确定）。
- NFR-P-02：客户端须能流畅渲染多模态消息与桌宠动画，不卡顿。

### 4.2 可用性与可靠性（NFR-A）
- NFR-A-01：服务端 7×24 在线，须具备异常自重启/守护能力。
- NFR-A-02：LLM API 调用失败须有降级/重试/友好提示。
- NFR-A-03：网络断连后客户端须能自动重连并同步离线消息。

### 4.3 安全性（NFR-S）
- NFR-S-01：所有凭据（服务器口令、API Key、DB 密码）走 `.env`，不进版本库；`.gitignore` 须覆盖。
- NFR-S-02：服务端 Web 面板与通信链路须有基础鉴权（单人场景至少一个访问口令/Token）。
- NFR-S-03：Redis 须设置访问认证，不暴露无密码端口。

### 4.4 可维护性与可扩展性（NFR-M）
- NFR-M-01：插件系统须模版化、低耦合，新增插件不改核心。
- NFR-M-02：LLM Provider 须抽象统一接口，便于新增模型源。
- NFR-M-03：配置驱动，核心行为可通过配置调整。

### 4.5 兼容性（NFR-C）
- NFR-C-01：客户端目标系统 Windows 11（兼顾 Win10）。
- NFR-C-02：服务端兼容 CentOS 7（注意其 Python/glibc 版本较旧带来的依赖约束）。

## 5. 数据需求

### 5.1 持久化数据
- **云端 Redis**：聊天记录（含时间/心情/状态）、人设、记忆、动态状态等。
- **客户端本地**：聊天记录缓存（可设上限）、人设 JSON、表情包资源、背景图、配置。
- **人设结构**：参考 `persona_雷姆.json`（完整五维：人设指令/描述/性格/场景 + 元数据），并扩展**语言、图片**字段。

### 5.2 数据同步
- 客户端本地持久化后须同步至云端 Redis。
- 离线期间产生的数据须在重连后同步。

## 6. 关键用例（摘要）

| 用例 | 主参与者 | 流程摘要 |
|---|---|---|
| UC-01 多模态聊天 | User | 用户发文字/图/语音 → 服务端多模态理解+LLM+插件 → 返回文字/语音/图/表情包 → 本地+云端持久化 |
| UC-02 创建聊天对象 | User | 面板创建/导入人设 JSON + 上传图片 + 配模型 → 持久化 → 客户端出现新会话 |
| UC-03 反向优化人设 | User | 导入聊天记录或删除「不符合人格」的回复 → 系统学习总结 → 更新人设 |
| UC-04 桌宠交互 | User | 最小化→桌宠 → 收消息抖动 → 点击展开聊天 → 最小化回桌宠 |
| UC-05 代人聊天 | User | 面板一键关闭大模型 → 用户手动代答 → 记录入库 → 用于反推人格 |
| UC-06 插件按对象配置 | User | 为聊天对象 A 开启 TTS+心情插件，为 B 开启图像插件+记忆插件 |
